# TrustVault

TrustVault is a document-vault web application: users upload documents, keep
full control over their own files and share them explicitly with other
accounts. Every state-changing action is recorded in a tamper-evident audit
trail.

The backend is a Node.js / Express / CommonJS application that talks to
PostgreSQL (Neon in the current setup) and authenticates with server-side
sessions.

## Requirements

- Node.js 20 or newer (developed and tested on Node 24)
- A PostgreSQL database (a Neon database works without any change)
- A second, **separate** PostgreSQL database for the automated tests

## Installation

```bash
npm install
cp .env.example .env     # then fill in the real values
```

### Environment variables

| Variable | Required | Description |
| --- | --- | --- |
| `PORT` | no | HTTP port, default `3000` |
| `DATABASE_URL` | in production | PostgreSQL connection string of the application database |
| `TEST_DATABASE_URL` | for the tests | Connection string of a **dedicated, empty** test database |
| `SESSION_SECRET` | in production | ≥ 32 characters, used to sign session cookies and derive CSRF tokens |
| `TRUST_PROXY` | no | Number of trusted reverse proxies, default `1` |
| `RATE_LIMIT_API` | no | API requests per 15-minute window and client IP, default `1000` |
| `RATE_LIMIT_AUTH` | no | Authentication requests per 15-minute window and client IP, default `30` |
| `UPLOAD_DIR` | no | Directory of the write-through file cache, default `./uploads` |

Generate a suitable session secret with:

```bash
node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"
```

The application **refuses to start** in production when `DATABASE_URL` or a
valid `SESSION_SECRET` is missing. In development it falls back to a clearly
marked development secret, which is rejected as soon as `NODE_ENV=production`.

### Database

```bash
npm run migrate     # applies src/schema.sql and the constraint fixes
npm run seed        # optional demo data (refuses to run in test/production)
npm start           # starts the server
```

`npm run migrate` is idempotent: running it twice against the same database
changes nothing and exits with code `0`.

`src/schema.sql` is the single source of truth. `src/scripts/schema.sql` is a
generated byte-identical copy; `npm run schema:sync` regenerates it and the
test-suite fails when the two drift apart.

## Running the tests

```bash
npm test
```

The suite runs against `TEST_DATABASE_URL` **only**. It never touches the
development or production database — `src/config.js` aborts the process when
`TEST_DATABASE_URL` is missing, points at the same database as
`DATABASE_URL`, or names a database that does not contain the word `test`.

See [`docs/TESTING.md`](docs/TESTING.md) for the details.

## Security summary

- **Authentication** — server-side sessions in PostgreSQL (`user_sessions`),
  `HttpOnly`, `SameSite=Lax` cookies, `Secure` in production, session id
  regenerated on login, `rolling` expiry.
- **Brute force** — a per-account lockout after five failed logins in a
  15-minute window, plus a dedicated rate limiter on the authentication
  routes.
- **CSRF** — double-submit token via `csrf-csrf`, bound to the session id.
  Login and registration are exempt because no authenticated session exists
  yet; they are protected by the lockout and the rate limiter.
- **Authorisation** — administrators have **no** implicit access to
  documents. Owners have full control of their own documents. Other users
  need an explicit grant, and `edit` never implies `delete`, `share` or
  `revoke`.
- **File uploads** — the content type is detected from the file itself, not
  from the extension or the client-supplied MIME type.
- **Audit trail** — every entry stores the SHA-256 hash of its own canonical
  representation and the hash of its predecessor. The database rejects
  `UPDATE` and `DELETE` on the log with a trigger.
- **Error handling** — clients only ever receive allow-listed messages; SQL
  text and stack traces stay in the server log.

The full threat model is in [`THREATS.md`](THREATS.md).

## Known limitations

- The audit chain is **tamper-evident, not tamper-proof**: an attacker with
  write access to the database can rewrite the log and recompute the hashes.
  The chain detects accidental and partial tampering, not a determined
  database administrator.
- `TRUNCATE` on the audit log bypasses the append-only trigger. The
  independent head anchor still detects the removal afterwards.
- The blobs are stored in the PostgreSQL database. For large files an
  object store should replace `document_blobs`.
- The login lockout is kept in the process memory, so it is per instance.
  With more than one application instance it has to move into the database or
  into a shared cache.
- In the frontend, the "Upload" navigation entry and "Upload document" button
  are strictly restricted to `document_owner` accounts and hidden for `admin`
  and `viewer` roles. The backend enforces `requireRole("document_owner")` on
  the `/api/documents/upload` endpoint and returns `403 Forbidden` for any
  unauthorized upload attempts. See [`docs/PERMISSIONS.md`](docs/PERMISSIONS.md).
